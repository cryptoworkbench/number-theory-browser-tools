- `euclidSteps(240, 46)` produces exactly 5 steps and `gcd === 2`:
  step 1 `{a:240, b:46, q:5, r:10, s:1, t:-5}`
  step 2 `{a:46, b:10, q:4, r:6, s:-4, t:21}`
  step 3 `{a:10, b:6, q:1, r:4, s:5, t:-26}`
  step 4 `{a:6, b:4, q:1, r:2, s:-9, t:47}`
  step 5 `{a:4, b:2, q:2, r:0, s:23, t:-120}`
  Returned `{gcd:2, s:-9, t:47}` — and `-9·240 + 47·46 = -2160 + 2162 = 2`.
- Row invariant, true of every step for every input: `a === q*b + r`, `0 <= r < b`, and `s*A + t*B === r` where `A`,`B` are the two normalized inputs.
- `euclidSteps(36, 36)` produces 1 step `{a:36,b:36,q:1,r:0,s:1,t:-1}` and `{gcd:36, s:0, t:1}`.
- `euclidSteps(17, 0)` produces 0 steps and `{gcd:17, s:1, t:0}`.
- `euclidSteps(500000, 2)` produces 1 step with `q === 250000`, `r === 0`, `gcd === 2`.
- Inputs are normalized before the trace so the larger value leads: entering `46` and `240` traces `240 = 5·46 + 10` first, not a degenerate `46 = 0·240 + 46` swap step. A visible note says the inputs were swapped and that the GCD is symmetric.

Math helper — one function, `euclidSteps(a, b)`, implementing the forward extended-Euclidean recurrence from `02-RESEARCH.md` Pattern 3. Seed `r0 = a, r1 = b, s0 = 1, s1 = 0, t0 = 0, t1 = 1`; while `r1 !== 0` compute `q = Math.floor(r0 / r1)`, `r2 = r0 - q*r1`, `s2 = s0 - q*s1`, `t2 = t0 - q*t1`, push `{a: r0, b: r1, q: q, r: r2, s: s2, t: t2}`, then shift each pair forward. Return `{steps: steps, gcd: r0, s: s0, t: t0}`. Do not write a second base-only helper: `s`/`t` cost two integer operations per step and a separate loop would duplicate the algorithm. Plan 02-04 consumes the `s`/`t` already attached here, which is what makes D-02's single unified table possible without a second animation pass. Plain `Number` arithmetic throughout — no `BigInt`; this tool has no cryptographic-realism reason to need it and the input cap keeps every value exact.

Input reading — a `readInputs()` returning `null` on rejection after writing one specific sentence to `errorBox` via `textContent` (never `innerHTML`: this is the one place a raw typed string reaches the page, and `textContent` is the repo's documented guardrail for it). Declare `MAX_INPUT = 1000000` as a named constant. Rules, each with its own message: a field that is empty or does not parse as a whole number is rejected; a negative value is rejected; a value above `MAX_INPUT` is clamped down to `MAX_INPUT` and the clamp is announced in `errorBox` (a cap is never silent); both values zero is rejected because `gcd(0, 0)` is undefined. Then normalize: `A = max`, `B = min`. When normalization actually swapped the typed order, write one sentence into `swapNote` saying the larger value leads and that the GCD is symmetric in its arguments; otherwise clear `swapNote`.

Render — `appendStepLine(step, index)` creates a `div.eq-line` carrying `data-a`, `data-b`, `data-q`, `data-r`, `data-s`, `data-t` set from that step, and inner spans `span.eq-num.eq-a`, `span.eq-op`, `span.eq-num.eq-q`, `span.eq-op`, `span.eq-num.eq-b`, `span.eq-op`, `span.eq-num.eq-r` rendering the classic division-algorithm form `240 = 5·46 + 10` with `·` as the multiplication sign, per D-03. `.eq-a` reads `var(--slot-a)`, `.eq-b` and `.eq-q` read `var(--slot-b)`, `.eq-r` reads `var(--slot-r)`. Lines append downward with a short fade-in CSS transition so the chain reads as a derivation being written out. Every value interpolated into a line is a computed integer, so template-literal interpolation is safe here; the raw `<input>` string is never interpolated into markup. `renderAnswer(run)` writes `gcd(A, B) = G` into `answerLine` styled with `var(--slot-answer)` and a soft background, matching how every other tool on this site marks its computed answer; `answerLine` is emptied by `resetPlayback()` and filled the moment the last step lands.

Playback — copy the engine shape from `Square And Multiply/square-and-multiply.html:395-401,643-725`, which is the `generation`-counter member of the same `play`/`pause`/`stepOnce`/`instantFinish`/`frameStep` family `02-RESEARCH.md` Pattern 1 documents in the Sieve and Completing-the-Square. Keep the function names, the module-scoped `playing` / `rafId` / `lastAdvance` / `stepIndex` / `generation` state, and the `SPEED_LABELS` and `SPEED_MS` tables verbatim. Use the time-based per-step dwell rather than the Sieve's events-per-frame counter: a GCD trace is five to fifteen steps, and an events-per-frame loop would consume the whole trace in three frames with nothing to watch. `advanceOne()` appends one line, increments `stepIndex`, snapshots `generation` before rendering and bails if it changed mid-call, and calls `renderAnswer` when `stepIndex` reaches the end. `play()` rewinds via `resetPlayback()` when the run is already finished, so Play always plays without a manual Reset first. `pause()` cancels `rafId`. `instantFinish()` pauses then appends every remaining line at once. `resetPlayback()` increments `generation`, zeroes `stepIndex`, empties `chain` and `answerLine`, re-enables `stepBtn`, and writes the ready sentence into `banner`.

`buildRun()` reads and validates inputs, calls `euclidSteps`, stores the result, calls `resetPlayback()`, then calls `instantFinish()` so the page never shows an empty derivation after a Run — the same auto-reveal-then-rewind contract the Square and Multiply template uses.

Event wiring at the bottom: `runBtn` click and `Enter` in either input call `buildRun()`; `playBtn` toggles play/pause; `stepBtn`, `instantBtn`, `resetBtn` call their functions; `speedInput` input updates `speedLabel`. Finish with `window.addEventListener('load', ...)` calling `buildRun()` so the page opens on a complete worked example for 240 and 46.
