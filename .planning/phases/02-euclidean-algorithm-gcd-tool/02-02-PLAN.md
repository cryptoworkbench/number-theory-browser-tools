Give the tool its one-click example roster and make the GCD ↔ shared-prime-factors connection discoverable from both sides: seven preset chips covering every category D-04 requires (including the `gcd(a, 0)` pair that terminates before the chain has anything to grow), and the two-way Venn Diagrams cross-link D-05 asks for.

This plan is the cheapest expansion outward from that slice — it adds no new subsystem, only new entry points into the one that already works, and in doing so forces the one code path the tracer could not reach: a run with zero steps. That path (02-RESEARCH.md Pitfall 4) breaks the growing-chain UI rather than the math, so it is fixed here, alongside the preset that makes it reachable in one click, not left for the geometric view to trip over.

Output: a `#presetChips` row inside the existing controls panel, a terminal-state note for zero-step runs, and one `p.xref` anchor on each of the two pages.

There is no way to parallelize edits to a one-file tool.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| keyboard → `#aInput` / `#bInput` → page DOM | Unchanged from plan 02-01: the two number fields are still the only untrusted input. This plan adds a second way to *fill* them, not a second way to bypass them. |
| `data-a` / `data-b` attributes in static markup → `buildRun()` | New surface. Author-controlled values in the shipped HTML, but reachable by anyone with devtools on their own machine. |
| relative anchors → sibling tool pages | New surface. Same-site, same-origin, no query string, no `target`. |

No network call, no server, no authentication, no session, no new storage key. Both files remain 100% client-side static HTML, CSS and JavaScript over `file://` or plain static hosting.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
