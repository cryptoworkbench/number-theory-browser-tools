  <files>Cayley Table Generator/cayley-table-generator.html</files>
  <precondition>`google-chrome` is on PATH (verified at `/usr/bin/google-chrome` during planning); the sizing, sticky-header and timing gates below all run through headless Chrome — if it is absent, halt and report rather than skipping them.</precondition>
  <behavior>
The breakpoint table this task must implement, and the derivation behind every number — 05-RESEARCH.md Pitfall 2 flagged the Sieve's own thresholds as *not* transferable because the Sieve's cell count grows linearly in its input while this table's grows quadratically, and A2 tagged the floor as an assumption to re-derive. This is the re-derivation; the numbers are keyed to `M`, the current mode's element count, never to `N`.

| M (elements in the current mode) | `--cell-min` | Table width at (M+1) cells | Fits the ~976px content column? |
|---|---|---|---|
| ≤ 12 | 46px | 13 × 46 = 598px | yes |
| ≤ 20 | 40px | 21 × 40 = 840px | yes |
| ≤ 32 | 34px | 33 × 34 = 1122px | no — horizontal scroll begins |
| ≤ 48 | 29px | 49 × 29 = 1421px | no |
| ≤ 72 | 25px | 73 × 25 = 1825px | no |
| > 72 | 22px | 121 × 22 = 2662px at M = 120 | no |

So cells shrink first, across roughly M = 6 to M = 24, and only then does the container take over and scroll — which is exactly the ordering D-02 asks for.

The 22px floor is derived, not picked: at `MAX_N = 120` the widest value a cell can hold is three digits (`119`), the cell font resolves through `clamp(9px, calc(22px * 0.40), 15px)` to 9px, and three 9px JetBrains-Mono digits advance about 16px, leaving room inside 22px minus the 2px separators. 22px also stays above the ~20px below which a pointer target stops being reliably hittable — and unlike the Sieve's inert display cells, every cell here is clickable, so the floor must respect that.

Expected `--cell-min` readings, which the harness asserts as computed values:
- N = 6 additive (M = 6) → 46px. N = 12 additive (M = 12) → 46px. N = 20 additive → 40px. N = 30 additive → 34px. N = 40 additive → 29px. N = 60 additive → 25px. N = 100 additive → 22px. N = 120 additive → 22px.
- N = 120 **multiplicative** → φ(120) = 32 elements → 34px, not 22px. This is the assertion that proves the function is keyed to M rather than N; getting 22px here means the wrong variable was passed.
- N = 100 multiplicative → φ(100) = 40 elements → 29px.

Expected font sizes, which follow from the same property: 15px at M = 6 (the clamp's upper bound, since 46 × 0.40 = 18.4), and 9px at M = 120 (the lower bound, since 22 × 0.40 = 8.8).

Performance budget, measured in the harness rather than assumed: building the 120 × 120 additive table completes in under 600ms, and a single cell click at that size completes in under 60ms. The click budget is the real test of 05-RESEARCH.md Pitfall 3 — an O(M²) highlight pass would blow it, an O(M) pass will not come close to it.
  </behavior>
  <action>
Replace the single static `--cell-min` value from plan 05-01 with a computed one, and prove the scroll path at the ceiling.

Add `cellMinPx(M)` to the file's helper section as a six-branch step function returning the pixel values in the behavior table above, taking the element count `M` — not `N`. Write a short comment naming *why* it keys on `M`: multiplicative mode's table is φ(N)×φ(N), which at `N = 120` is 32×32 against additive's 120×120, and shrinking the units table to the floor for a modulus it never had 120 elements at would be a bug the learner would feel as a wall of tiny cells for no reason.
