<interface_notes>
Facts already established in the files above — do not re-derive them:

- `svg#wheel` is `viewBox="0 0 900 900"`; `CX = CY = 450`, `HOLE_R = 55`, `OUTER_R = 400`. The furthest-out ink is the per-wedge ellipsis glyph at radius `OUTER_R + 18 = 418` (font-size 15), so all drawn content lies inside the 900x900 viewBox and a full-viewBox background rect covers the whole diagram.
- `render()` clears and rebuilds `#wheel-dynamic` on every slider input and every `select(idx)`. The export code must read the DOM at click time rather than caching anything, and must not be called from inside `render()`.
- The wheel's colors reach the SVG two different ways, and the export has to handle both: (a) CSS rules in the page's `<style>` block (`.cell-num`, `.wedge-hit`, `.ellipsis`, `.center-label`) and (b) inline presentation attributes written by `svgEl()` as literal `var(--token)` strings (`stroke:'var(--surface-alt)'` on the zebra bands, `'var(--panel-border)'` / `'var(--panel-border-strong)'` on the ring and radial boundaries). Neither survives serialization on its own: a standalone SVG has no stylesheet and no custom properties.
- Non-selected `.wedge-hit` paths compute to `opacity: 0`; the selected one computes to `opacity: 1`, `fill: var(--accent-soft)` (a `color-mix()`, so its computed value carries alpha), `stroke: var(--accent)`, `stroke-width: 1.6`.
- `state` is `{ N, depth, selected }`. `N` (1-60) and `depth` (2-10) are range-validated on load from the `congruence-wheel` localStorage key; `selected` is never read from storage and only ever set from a loop index.
- `assets/theme.js` writes the theme to localStorage/cookie ONLY inside `setTheme()` (the toggle's `change` handler) and on the `storage` event. It never observes the `data-theme` attribute. Setting `data-theme` directly on `document.documentElement` therefore changes appearance only — it does not persist, and it does not touch `#theme-switch-input.checked`, so restoring the previous attribute value restores the exact prior state. Do not route the print theme flip through `setTheme()`.
- Button styling convention to imitate lives in `Sieve Of Eratosthenes/sieve-of-eratosthenes.html` lines 118-150 (`.btn-row`, the base button rule: `font-family:inherit`, `font-size:.88rem`, `font-weight:600`, `color:var(--text)`, background and hover built from `color-mix(in srgb, var(--text) N%, transparent)`, `border:1px solid var(--panel-border)`, `border-radius:10px`, `padding:8px 14px`, `transform:scale(0.96)` on `:active`).
- This file already styles bare `button` elements through the `.row-btn` class (the residue-class list, which deliberately has no background and no border). New button CSS must be class-scoped, never a bare `button` selector, or it will bleed into that list.

<pdf_approach_decision>
The constraint offers two no-library PDF routes. This plan takes (a), the native print route, and does not hand-assemble PDF bytes. Reasons, in order of weight:

1. **Output quality is strictly better.** The browser's print pipeline renders the live SVG, so the resulting PDF is *vector* — infinitely zoomable, selectable digits, and it uses the real JetBrains Mono webfont already loaded in the document. Route (b) can only wrap the rasterized PNG, so it would ship a fixed-resolution image inside a PDF wrapper: a worse artifact than the PNG the user can already download.
2. **Route (b) is unverifiable here.** A hand-built PDF needs a correct byte-offset xref table; a one-byte error yields a file that silently fails to open. This repo has no test harness (CLAUDE.md: verification is opening the file in a browser), so a subtly invalid PDF would be caught by the user, not by us. The print route cannot emit a malformed file because we do not author the file.
3. **It is a quarter of the code.** Roughly 25 lines of `@media print` CSS plus an idempotent theme-flip pair, versus a deflate/xref/object-graph writer.

The tradeoff accepted: the user passes through the browser's print dialog and picks "Save as PDF" / "Microsoft Print to PDF" rather than getting an immediate file. The button is labelled for exactly that — "Print / Save as PDF" — so the control never over-promises.
</pdf_approach_decision>
