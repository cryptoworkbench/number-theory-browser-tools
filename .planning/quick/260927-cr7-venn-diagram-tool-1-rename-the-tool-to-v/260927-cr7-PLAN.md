Behaviour proven in the actual target browser (`google-chrome --headless`, window 1200x2400) before this plan was written — the drag design below rests on these four facts, so none of them is a guess:

1. `document.elementFromPoint` over a region resolves to `path.region-hit`, and `.closest('.region')` on it returns the region group (`region-right`). `closest` works on SVG elements here.
2. Synthetic `PointerEvent`s dispatched on `window` are received by `window`-level listeners, so the gesture is automatable without the DevTools protocol.
3. Setting `pointerEvents = 'none'` on `#venn-dynamic` makes `elementFromPoint` at a placed chip's own centre resolve to the region path beneath it (`region-left`). This is the fix for "the thing you are dragging hides the thing you are dropping onto".
4. `elementFromPoint` returns `null` for coordinates outside the viewport — which is why the harness must run at a tall window size, and why the verify commands below all pass `--window-size=1200,2400`.

Add drag-to-move for already-placed tokens, per D-02, wired for the two-circle mode and built on a helper that Task 3 reuses verbatim for three-circle. Everything stays inside the existing inline `<script>` and inline `<style>` — no new file, no dependency (NAV-02).

Why pointer events and not the HTML5 drag API the picker chips use: the `draggable` attribute is an HTML global that SVG elements do not carry, so `dragstart` does not fire reliably on an SVG `<g>` across the four browsers this project supports. A pointer-event gesture is the one mechanism that works everywhere and leaves the SVG rendering untouched. The picker chips' existing `dragstart`/`drop` path is not modified — the two mechanisms do not overlap, since the new listeners attach only to placed tokens.

State move. Add `moveToken(fromKey, toKey, id)` beside `removeToken`. It returns immediately if `fromKey === toKey`. Then — **before mutating anything** — it checks `state.regions[toKey].length >= MAX_PER_REGION` and on a full target emits the region-is-full warning and returns, leaving both lists untouched (D-03: reject, never evict). Only then does it locate the entry by `id` in the origin list with the same index loop `removeToken` already uses, `splice` it out, and `push` that same `{id, p}` object into the target list — same object, same `id`, so no new state shape and no re-parsed payload is introduced. It finishes with `persist()`, a `setMessage` line naming the prime and the target region's `REGION_CAPTIONS` entry in the same voice as the existing "Placed"/"Removed" lines, and `render()`.

To keep one wording for the full-region warning, extract the warning `setMessage` call that `placePrime` already makes into a one-line `warnRegionFull(key)` helper and have both `placePrime` and `moveToken` call it. Do not reword the message — it is the string D-03 asks to reuse.

Gesture harness. Add `wireTokenDrag(g, ctx, regionKey, tokenId)` and a module-level `var dragSuppressClick = false;`. `ctx` is a small descriptor built once: `{ els: regionEls, dynamic: svgDynamic, move: moveToken }`. Task 3 passes the three-circle equivalent, so keep the helper free of any two-circle-specific reference.

On `pointerdown` on the token group: ignore it unless `ev.isPrimary` and, for `pointerType === 'mouse'`, `ev.button === 0`. Reset `dragSuppressClick` to false, record the start `clientX`/`clientY`, compute the screen-pixel-to-SVG-user-unit scale once as `g.ownerSVGElement.viewBox.baseVal.width / g.ownerSVGElement.getBoundingClientRect().width` (guard a zero width by bailing out of the gesture), and attach `pointermove`, `pointerup` and `pointercancel` listeners on `window` — not on the element, and not via `setPointerCapture`, because the dragged group is about to stop taking pointer events.

On `pointermove`: until the pointer has travelled more than 4px from the start, do nothing — this is what keeps a plain click working as click-to-remove. On first crossing the threshold, call `ev.preventDefault()`, add `is-dragging` to the token group, and set `ctx.dynamic.style.pointerEvents = 'none'` so that neither the dragged token nor any sibling token hides the region beneath the pointer (proven fact 3 in `<grounded_facts>` — without this, dropping onto an occupied region silently fails). While dragging, track the pointer by setting a `transform` of `translate(dx * scale, dy * scale)` on the token group, so the token follows the cursor in user units rather than lagging by the viewBox scale factor.

On `pointerup`: detach the three window listeners, restore `ctx.dynamic.style.pointerEvents`, remove `is-dragging`, and clear the `transform` — always, and before any state call, so a rejected or no-op drop snaps the token back where it was. If the threshold was never crossed, stop there and let the existing click handler remove the token. Otherwise set `dragSuppressClick = true`, resolve the drop target by calling `document.elementFromPoint(ev.clientX, ev.clientY)`, taking `.closest('.region')` on the result, and matching that element by identity against the values of `ctx.els` to get its key — identity matching, not id-string parsing, so a region belonging to the other mode can never be resolved. If no region resolves, return (D-03: dropping into empty space is a no-op). Otherwise call `ctx.move(regionKey, resolvedKey, tokenId)`. Treat `pointercancel` exactly like a pointerup that resolved no region.
