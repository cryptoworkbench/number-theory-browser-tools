<objective>
Add Brazilian Portuguese (`pt-BR`) and European Portuguese (`pt-PT`) as the eighth and ninth supported languages site-wide, following quick tasks 261002-c77 (Italian) and 261002-fmi (Polish) step for step:
- the engine allow-list;
- two switcher options on all 16 pages;
- complete pt-BR and pt-PT dictionaries in all 18 namespaces (site + common, hub, 15 tools);

- nine-language gate tooling and nine-language docs.

On top of that template, this task generalizes the language-code shape. NT.i18n has so far assumed two-letter codes. It must now accept the region-tagged codes `pt-BR` and `pt-PT` exactly (case-sensitive, rejecting everything else), and detect them from the browser language with a region rule. The existing seven languages' behavior and English output stay byte-identical.

Purpose: a visitor whose browser prefers Portuguese, or who picks either variant in the header, gets every page in Brazilian Portuguese (você, Brazilian spelling and vocabulary) or European Portuguese (tu, European spelling and vocabulary). Either variant gets the same persistence, cross-tab sync, link carry and no-reset re-render as the other seven languages.

- a `'pt-BR': {...}` and a `'pt-PT': {...}` block after `pl` in each of the 17 data files;

- an `i18n-check.js` that covers nine languages, accepts region-tagged switcher options and asserts the new code shape;
- an updated glossary, living docs and five i18n-config reason strings.

**Planner-discretion decisions.** This quick task has no CONTEXT.md. The decisions below are recorded here and referenced as Q-NN in task actions. Q-01's labels, Q-02's exact-match rule and Q-03's mapping are fixed by the task description; the rest are planner discretion.

- **Q-01 Switcher.**
  - Two lines go directly after the Polski option, pt-BR first: an option with value `pt-BR`, lang `pt-BR`, label `Português (Brasil)`; then value `pt-PT`, lang `pt-PT`, label `Português (Portugal)`.
  - Same 8-space indentation, no `selected` attribute.
  - Both lines are byte-identical on all 16 pages, so `--header`'s canonical-header identity gate holds.
  - LANG_CODES, SWITCHER_OPTIONS and every data file use this same order: nl, en, de, fr, es, it, pl, pt-BR, pt-PT.
- **Q-02 Code shape and validation.**
  - A language code is now an exact BCP 47 tag from SUPPORTED_LANGS: a two-letter language subtag, or language-REGION with a lowercase language and an uppercase region (only `pt-BR`, `pt-PT`).
  - Validation stays the existing exact, case-sensitive `indexOf` in `valid()`, applied unchanged to `?lang=` (after decodeURIComponent, as today), the cookie, localStorage, the storage event, and setLang.
  - No channel normalizes case, separators or whitespace. So `pt`, `PT-BR`, `pt-br`, `pt_BR`, `pt-pt` and `' pt-BR'` are rejected, and a rejected `?lang=` value is not stripped from the URL (existing behavior).
  - The hyphen and ASCII letters need no encoding in the cookie value, in a link's `lang=` parameter, or in `<html lang>`, so persist(), decorateLinks() and applyHtmlLang() stay byte-identical.
- **Q-03 Browser-language detection (the only case-insensitive path).**
  - Within detectDefaultLang's loop, before the existing two-letter line, lowercase the tag and split it on `-` or `_`.
  - When the first subtag is exactly `pt`, the region is the first later subtag that is 2 letters or 3 digits. A script subtag such as `Latn` is skipped.
  - No region, or region `br`, returns `pt-BR`. Any other region (`pt`, `ao`, `mz`, `cv`, `419`, …) returns `pt-PT`.
  - Every other tag falls through to the existing line `var code = String(langs[i]).slice(0, 2).toLowerCase();` and the following `if (valid(code)) return code;`, both kept byte-identical. Results for every navigator list whose first supported match is not Portuguese are therefore unchanged. Before this change, a pt-primary tag always produced the invalid two-letter `pt` and was skipped; DETECT-PARITY proves this over 6799 navigator lists.
  - The code is ES5 like the rest of the file: `var`, plain `for` loops, no arrow functions, no `Array.prototype.find`.
- **Q-04 Register.**
  - pt-BR uses **você**. Instructions are third-person imperatives (clique, digite, escolha, pressione, veja, tente, arraste, insira); possessives are seu/sua. This is the standard Brazilian UI register.
  - pt-PT uses informal **tu**. Instructions are second-person-singular imperatives (clica, escreve, escolhe, prime, vê, tenta, arrasta, insere); possessives are teu/tua. This matches nl je / de du / es tú / it tu / pl ty.
- **Q-05 Spelling, vocabulary and notation.** Both variants follow the 1990 Orthographic Agreement as each country applies it.
  - pt-BR:
    - fator, fatoração, ação, direção, ótimo; circumflex forms econômico, fenômeno, polinômio, binômio, gênero;
    - vocabulary: arquivo, tela, registro (a log heading is `Registro`), usuário, compartilhar, de fato;
    - grammar: proclisis (`se encaixa`) and the gerund progressive (`está calculando`).
  - pt-PT:
    - fator, ação, direção, ótimo, but fatorização, facto, receção; acute forms económico, fenómeno, polinómio, binómio, género;
    - vocabulary: ficheiro, ecrã, registo (a log heading is `Registo`), utilizador, partilhar;
    - grammar: enclisis (`encaixa-se`) and `estar a` + infinitive (`está a calcular`).
  - GCD/LCM: where a data file already localizes the gcd/lcm notation or the prose noun "the GCD" (its it/es/pl blocks show `mcd(`, `NWD(`, `ggT(`, "il MCD", "NWD"), pt-BR uses `mdc(` / `mmc(` and the noun `o MDC`, and pt-PT uses `m.d.c.(` / `m.m.c.(` and the noun `o m.d.c.`. Each choice is used consistently in casing across its whole block (Italian deviation 2).
  - Where a file keeps `gcd`/`lcm` literal in every language (its header says so, e.g. chinese-remainder-theorem.js), both variants keep it literal.
- **Q-06 Punctuation and capitalization.**
  - Quotes, if ever needed: “…” in pt-BR, «…» in pt-PT.
  - No space before `:` `;` `?` `!`.
  - Headings and tool names use sentence case (first word and proper nouns only), like fr/es/it/pl.
  - A value containing a straight ASCII apostrophe must be double-quoted, like the French nav values in site.js.
- **Q-07 Plurals.** CLDR 48 (node 22 / ICU 78.2, verified at planning time) gives:
  - pt-BR (which Intl resolves to `pt`): one = integer part 0 or 1, so 0, 1, 0.5 and 1.5 select `one`;
  - pt-PT: one = exactly 1, so 0 and 1.5 select `other`;
  - both: `many` for exact multiples of 1,000,000.

  So every Portuguese plural value is `{ one, other }` in that key order, exactly like fr/es/it. The `many` category has no key and falls back to `other` in the unchanged engine. `PLURAL_EXTRA_CATEGORIES` stays `{ pl: [...] }`.

  pt-BR rendering its `one` form at count 0 is deliberate: it is CLDR's rule, the engine follows it, and it is the same thing French already does (`--api` asserts fr 0 → one). Word the pt-BR `one` form as a normal singular; do not neutralize it into a label form.

  Every Portuguese plural value has `one` ≠ `other` (the noun is always inflected: elemento/elementos, passo/passos, bit/bits). Its `one` carries English one's placeholders, and its `other` carries English other's.
- **Q-08 Proper nouns.**
  - Euclid → **Euclides** and Eratosthenes → **Eratóstenes**, the conventional Portuguese forms (shared with es; both are already NEUTRAL_TOKENS).
  - Euler, Fermat, Cayley, Venn, Shor, Bézout, Diffie-Hellman, RSA, DH, ECDH and Sun Tzu are invariant.
  - Alice, Bob and Eve are kept per glossary (d). Portuguese does not decline names.
- **Q-09 Gate lists.**
  - i18n-check.js keeps ONE `LANG_CODES` and ONE `SWITCHER_OPTIONS` list, each gaining both codes.
  - checkSwitcherPresent's option regex accepts an optional `-` + two uppercase letters after the two lowercase letters, on both value and lang. The comparison against SWITCHER_OPTIONS stays exact, so a wrong case, an underscore, a missing option or a wrong order is still a finding (SWITCHER-GATE proves it, and proves the old regex fails).
  - The `--api` SUPPORTED_LANGS pin stays an independent, hand-written, sorted literal.
  - i18n-browser.js derives from the exported `LANG_CODES` and needs no edit.
- **Q-10** `--smoke` keeps its existing fr/es/de probe and `buildExpected` unchanged. Portuguese runtime coverage comes from i18n-browser.js on all 16 pages.
- **Q-11 Fix policy.**
  - Fixes for overflow or untranslated text go into Portuguese wording.
  - A genuine Portuguese cognate identical to English is handled per key. The exemptions are language-agnostic, so the gate already passes for a key that has one. Extend that key's existing `allowSame` reason string, and its mirrored `allowRenderText` reason where one exists, to name Brazilian and European Portuguese, as Polish did. A cognate on a key without an exemption gets a new `allowSame` + `allowRenderText` pair with a concrete reason. Polish deviation 1: the runtime check needs `allowRenderText` too.
  - Expected cognates: `zero` (cayley.identityWordAdditive), `bit` (rsa.thBit / rendered `bit`), `Base b` (sqm.baseLabel), `base a` (shor.legendBase) and `final` (fermat.legendFinal).
  - Never fix by editing page CSS, markup or script (that breaks en-parity), and never by loosening a gate, a marker list or a threshold.
  - Known non-cognates to keep distinct from English: `ordem` (ecdh.ordWord, dh.orderLabel `ordem(g) = `), `Gerador g` (dh.gLabel), `Ponto (…)`, `Expoente e`, `expressão`, `múltiplos`.
- **Q-12 Accepted header consequence.** "Português (Portugal)" is the longest autonym, so it widens the native select on every page and in every language, English included.
  - Measured at planning time in a scratch mirror at 375px: the select grows from 105px to 159px, and the tool-page header grows from 229px to 264px because it wraps one more row. index.html stays at 270px. There is zero horizontal overflow, and no change at 1280px.
  - This follows from the locked labels, and en-parity is unaffected because it strips the switcher. Do not change `assets/site.css`, page markup or the labels.
  - HEADER-375 pins zero horizontal overflow. Record the measured header heights in the SUMMARY so the user can decide on any follow-up.
- **Q-13 Authoring flow.**
  - In each data file, append `'pt-BR': { ... }` and then `'pt-PT': { ... }` after the `pl` block (pl's closing brace gains a comma), with quoted keys.
  - Write pt-BR first, then derive pt-PT from it as a real adaptation per Q-04/Q-05. Never copy a pt-BR value verbatim into pt-PT when it contains an imperative, a second-person pronoun or possessive, a clitic, a progressive, or a variant-specific word or spelling.
  - PT-VARIANT checks marker words in both directions and requires at least 50 differing values site-wide.
